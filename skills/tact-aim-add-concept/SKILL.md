# TACT-AIM 系 MOD へ新概念・新システムを追加する

対象: `TACT-AIM-MYTHOLOGY`（本命）と `TACT-AIM-MOD`。
新概念は「既存の仕組みの組み合わせで成立させる」のが流儀。エンジンの制約を
先に確定させ、その中で設計する。仕様判断は作者のもの。未確定の案は仮案として
一覧化し、報告で未確定と明示する。全体の流れと検証ゲートは親スキルに従う。

## 設計の前に確定させる制約

- **クラウド形式は固定長。** クラウド変数は「☁ CLOUD1〜10」の10個で Scratch の
  上限ちょうど。新しいクラウド変数は追加できない。新しい状態を同期したい場合は
  既存フィールドの空きや1文字フラグで表現する
  （例: スキン段階は field 25 の1文字で `"2"` までなら形式不変で入る）。
- **効果の語彙は既存分だけ。** 使える効果は既存の `Bullet_name` / `Buff_name` に
  ある名前だけ。完全新規の効果は受信側（Player_shot 等）の処理追加が別途必要で、
  規模が変わるので作者の判断事項として切り分ける。
- **detranspile は新規手順（メソッド）を作れない。** TS に新しいメソッドを足して
  他から `yield*` で呼ぶとビルドが `yield* unknown method` で落ちる。
  呼ばれない新規メソッドを残すと TS テストだけ通り sb3 に入らないので絶対にやらない。
  新規の毎フレーム処理は、既存手順の末尾へゲート付きで直接書く
  （実績: スロット本体を Draw_NPC 末尾に num==7 かつ Menu[19]==7 の条件で配置）。
  状態は Pen のクラスフィールドに持つ。
- **秒数は30fps換算のフレーム数で書く**（10秒 = 300）。
- project.json は Scratch の保存上限 5MB に注意。コンテンツ追加で近づいたら
  まず buildSb3 の ID 圧縮パスが効いているか（minify ログ）を確認する。

## 新システムの置き場所の流儀

- **定義表はフラットな const 配列**にする（SUPER_EFFECTS 方式）。
  const 配列は detranspile で Scratch リストとして実体化する
  （動的添字アクセスは0始まり +1 のずれに注意）。
- **発動は既存経路を再利用する。** 新しい発動方法を作っても、効果・同期・
  クールダウンは既存の発射/スキル経路に乗せると受信側の変更が不要になる
  （実績: スーパースキルは専用ショット番号 923+スキル番号で発動し、
  受信側 Player_shot が表を切り替えて読む）。
- **描画は毎フレーム再描画される既存手順の末尾**に足す（カットイン、ゲージ表示など）。
  状態は「残りフレーム数 + 表示内容」の変数で持つ。

## スーパースキル型（個別定義方式）

- 紐づけ方式ではなく **スキルごとに個別定義**するのが作者の方針
  （内容もカットインも別々に作るため）。
- 定義表は Pen_All.ts 冒頭の `SUPER_EFFECTS`（Skill_2 と同じ15フィールド形式:
  名前＋効果ペア最大3つ）。カットインの色は別表
  （SUPER_CUTIN_BAND / SUPER_CUTIN_ACCENT、スキル番号順）。
- カットインは短く（36フレーム ≒ 0.6秒、本人の画面のみ）。
  全員に見せるにはクラウドレコードへのフラグ追加が別途必要
  （受信側ではスーパーと通常発動を区別できない）。
- 既知の制約も設計に含める: 受信側の累計発動クールダウン（Skill_counter）は
  新システムの発動も対象になる場合がある。

## スキン段階の追加

- 段階は既存変数の値域を広げる（例: Special_skin 0/1 → 0/1/2）。
  クラウド送信が1文字フラグなら形式不変で入る。
- 描画分岐は**全経路**で足す: ゲーム内（体・手）、プロフィール、
  ロードアウトプレビュー、チーム一覧。手など一部コスチュームが無いキャラ向けに
  上位 → 下位への自動フォールバック（++ → + → 通常）を付ける。
- 解放条件が未確定なら、既存段階と同じ条件を仮仕様にして報告で明示する。

## バフの追加

- Buff 表（20フィールド/件）と Buff_name は**位置で対応**する。
  件数がずれている場合（実績: 名前72件・表79件）、新規バフは表の
  **名前件数にあたる位置へ挿入**し、Buff_name へも同じ位置に足す。
  末尾追加は対応がずれて静かに壊れる。
- バフアイコン `^<バフ名>` コスチュームが必須（無いと表示で化ける）。
- 持続は Put_buff の第2引数（フレーム数、30fps換算）。

## ロビー NPC / 新モードの追加

- All のロビー節に Draw_NPC 呼び出しを追加し、Draw_NPC 内に num 別の初期化分岐を足し、
  All の「離れたら Menu[19]=0」リセット条件にも新 num を足す。
- Draw UI の内容ブロックは Menu[19] の値ごとにゲートされているため、
  新モードでは既存 UI は何も描かない（独自 UI を描く余地がある）。
- **ただし Draw UI の Shop 面（共通枠）は全モード共通で開く。** モード固有の表示を
  Draw_NPC 等で別描画すると共通枠に上書きされる。モード固有の表示は
  Draw UI のタイトル分岐の直後（Menu[19] 判定）に描くこと。
  クリック判定は状態側（Draw_NPC 等）に残してよいが、矩形は盤面上の実位置に合わせる。
- 通貨は G.Money（ショップと共通）。課金系（スロット等）は期待値を全通り検算し、
  RTP を報告に書く（実績: スロットは全125通りで検算、RTP約95%）。

## 世界観・命名

- MYTHOLOGY は「神話・若干昔寄せ」が作者の方針（古代〇〇、初期型〇〇 など）。
  ただし世界観の具体化は作者が保留/確定する事項。指示があるまで着手しない。
- 名前・二つ名・説明文などのコピーは起案してよいが、仮置きとして報告で明示する。

## テストと検証

- 新システムは専用テストファイルを作る（pen-super / pen-skin の型）:
  定義表の分離、発動条件、段階の循環、表と名前の位置対応を検証する。
- ダイジェストは「変わらないこと」が正の場合と「追加由来の差分だけ変わる」場合を
  区別して報告する。その後の検証ゲートは親スキル `tact-aim-add-content` に従う。
