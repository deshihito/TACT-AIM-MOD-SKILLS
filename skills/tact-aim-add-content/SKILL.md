# TACT-AIM 系 MOD へコンテンツを追加する（総合）

> このスキルは親スキルです。種類別の詳細スキル:
> 武器は `tact-aim-add-weapon`、サブ/アイテムは `tact-aim-add-item`、
> キャラは `tact-aim-add-character`、新概念・新システムは `tact-aim-add-concept`、
> SVG は `tact-aim-svg-costumes`、sb3 検証は `tact-aim-sb3-round-trip`。
> push 前の一覧確認は `checklists/add-content-checklist.md`。


対象: `deshihito/TACT-AIM-MYTHOLOGY`（本命）と `deshihito/TACT-AIM-MOD`。
ローカル clone は `~/workspace/TACT-AIM-MYTHOLOGY`。distilled（原作の純粋コピー）には
MOD 用の追加を入れない。仕様の数値・デザイン判断はユーザーが決める。未指定の値は
仮置きとして実装し、報告で「仮置き」と明示する。

## 全体の流れ（追加の種類によらない）

1. 仕組みを実測で確認してから触る（下記の各手順の「調査」を省略しない）。
2. データ → ロジックフック → コスチューム → テスト → sb3 再生成 → push の順。
3. GitHub 書き込みは集約: 実装と検証を全部終えてから commit/push は各 1 回。
4. `MYTHOLOGY_NOTES.md`（MOD 側の共有ノート）に結果を残す。

## 検証ゲート（全て通過して初めて push）

- `npm test` 全合格。テストは `dist/` を import するので、TS を編集したら
  個別テストの前に必ず `npx tsc` を先に回す。
- 起動ダイジェストが変わるのは正常（データ追加で変わる）。再基準化の手順:
  1. 状態ダンプ（boot 15,000 フレーム後の G 全項目: スカラー全量＋リストは
     長さ・全要素ハッシュ・先頭3件＋penLines/stamps/errors/threads）を新旧で取る。
     旧側は `git worktree add /tmp/oldbuild HEAD` + `npm ci` + `npx tsc`。
  2. diff が「追加データ由来のリスト長と中身」だけであることを確認する。
     スカラーや描画カウンタに差が出たら実装ミスを疑う。
  3. `tests/boot.test.mjs` の EXPECTED_DIGESTS を更新し、ファイル内の履歴コメントの
     書式に倣って「日付＋何を追加したか＋全比較で差分が何だけだったか」を追記する。
- 件数を直書きしている既存テスト（例: pen-init の Weapon_name/Shop_menu/Bullet_name
  の長さ）も新しい件数へ更新する。
- `src/distilled/Pen_All/` 配下を編集したら `npm run detranspile:check-distilled` で差分が
  意図した文の追加・変更だけになっているか確認する（`assets.ts` / `state.ts` / `cloud.ts` / `world.ts` / `combat.ts` / `draw.ts` / `ui.ts` / `index.ts` に責務分割済み）。
- sb3: `mkdir -p out && npm run detranspile:build-distilled` →
  `python3 tools/validate_sb3.py out/*.sb3`（0 issues）→
  `bash tools/verify-distilled.sh`（BOOT TEST: PASS = 往復等価）。
  成果物を `~/workspace/TACT-AIM-MYTHOLOGY.sb3` へコピーし、`out/` は消す。
- sb3 の中身を直接確認する: 新コスチュームの存在、マニフェスト全アセットの同梱、
  ステージリストの長さ、クラウド変数が CLOUD1〜10 のみ。

## キャラ追加の手順

調査で確定させるもの: `Character_2` / `Character_tree` のレコード形式、
`G.Character`（0 始まりレコードオフセット）の使われ方、ダメージ決済の位置。

1. **データ**（`src/generated/lists/stage/`）:
   - `Character_2.ts` に 15 フィールド追加: [名前, スキル名, 攻撃, HP, 速度,
     音量倍率, 索敵範囲, 再生（負数）, ""×7]。
   - `Character_tree.ts` に 10 フィールド追加: [名前, x, y, 解放種別, 解放量,
     進捗, **リンク**, ""×3]。リンク = **親レコードの 0 始まりオフセット**
     （例: レコード 13 番目の親指定は 120 ではなく 110 のような値になる。
     既存レコードのリンク値と親子関係を 2〜3 組実測してから決める）。
     リンクに "m"+月 を入れると季節限定扱いで線が描かれない。
   - 座標 (x, y) はツリー画面のノード配置そのもの。親ノードの近くで
     既存ノードと重ならない空き場所を選ぶ（既存の間隔はおおよそ 100〜120 刻み）。
   - 解放種別はゲーム側が評価できる既存の文字列（"Block damage" など）を再利用する。
     新しい種別は評価側の実装が別途必要で、ユーザーの判断事項。
   - スキル名は既存スキルを指すこと。スーパースキルはスキル番号（Skill_2 の並び順）
     で SUPER_EFFECTS と対応するので、既存スキルの再利用なら自動で同じスーパーが付く。
     新スキルを作る場合は Skill_2 追加＋SUPER_EFFECTS 同位置追加＋スキル自体の
     実装が必要で、これもユーザーの判断事項（勝手に決めない）。
2. **起動時上書きの罠**: Pen_All の初期化が作者専用枠（Crystal Gobo / Gem Cat）を
   tree の決め打ち位置（item 231/241）へ書く。新キャラがその位置に来る場合は
   書込先インデックスを後ろへずらす（レコード追加のたびに衝突を確認）。
3. **特殊能力のフック**: 常時発動系（防御○○%など）はダメージ決済
   （`Bullet_damage`/`Bomb_damage` へ Buff_effect[3]/[4] を掛ける箇所）の直前で
   `G.Character_name` を見て係数を差し替えるのが既存の流儀。
   エンジンの床仕様を確認する: 弾ダメージは最低 1 に切り上げ、爆発は床なし
   （係数 0 で完全 0）。「100% 軽減」でも弾は 1 ずつ通ることを報告に書く。
4. **コスチューム**: body / body+ / hand / banner の 4 種＋神話 ++（下記「コスチューム」）。
   既存キャラの流用・変形は `tools/make_new_costumes.py` に処理を足す
   （再生成で Pen_All 登録行とマニフェストを差し替える作りになっている）。
   登録位置は Pen_All 内で流用元キャラの同種コスチュームの直後が既存の並び。
   **banner は必須**（無いとツリー画面でキャラ詳細が出ない）— 詳細は
   下記「バナー（キャラ詳細カード）」。
5. **神話スキン**: `tools/make_mythic_skins.py` の CHARS と CHAR_SPECS に追加。
   個別の描き下ろしは CHAR_EXTRAS（Cat/Gobo が前例）。この生成スクリプトは
   開始時にマニフェストと ++ アセットを消してから作り直すので、途中で落ちると
   マニフェストが消える。先に `make_new_costumes.py` を回して土台を復旧してから
   再実行する。
6. **テスト**: `tests/pen-newcontent.test.mjs` の型で、レコード内容・ツリー連結・
   フックの発火を検証し、`package.json` の test チェーンへ組み込む。

## 武器追加の手順

調査で確定させるもの: `Item_list` のレコード形式、弾プログラム（Bullet_list）の
文法、発射経路（Weapon_motion → Shot__c）、近接の Sword damage ハンドラ。

1. **データ**:
   - `Item_list.ts` に 14 フィールド追加: [名前, 種別, idx2（重量系）, 価格,
     idx4, idx5（idx6=1 のときズーム）, スコープ旗 idx6, idx7, idx8,
     サウンド id idx9, コスチューム名 idx10, **挙動文字列 idx11**, 弾名 idx12, ""]。
     価格欄の "mMM" は季節限定表記。
   - `English_weapon_name.ts` に英語名を 1 件追加（件数が Item_list と一致すること）。
   - `Bullet_list.ts` に弾プログラムを追加（"" 終端の可変長レコード）。
     近接は `["名前", "Sword damage", ダメージ係数, 射程, 弧度, ノックバック,
     "Length", 6, 14, "-"×6, ""]` が大剣の型。ダメージ係数は発射者の
     攻撃倍率（クラウド field 24）と掛け算される。
   - `src/distilled/Pen_All/state.ts` の `Bullet_name` SList の末尾に弾名を追加。
2. **反動で飛ぶ武器**: 挙動文字列に `近接反動NN` を入れる。推進力 = 50 − NN
   （大剣 = 近接反動20 → 30）。比率指定（例: 大剣の 1.5 倍 = 45）は NN = 05。
   反動は発射ごとの照準方向へ掛かる。
3. **連射・連鎖などの特殊挙動**: `Weapon_motion`（毎フレーム実行）に tick を置き、
   `Shot__c(G.Inventory, true)` のように Full へ真を渡すと強制発射できる
   （compare() の結果を直接渡す前例あり）。発射は記録され、受信側は発射者の
   現在の照準でデコードするので、連鎖の向きはマウスで制御できる。
   持ち替え検知は `G.Inventory_2.item(G.Inventory + 1)` と装備名の比較。
4. **コスチューム**: held（素の名前）/ @アイコン / *ショップカードの 3 種。
   ショップの並びは `*` コスチュームの連続走査で決まるので、* は既存の * 群の
   内側に置く。sb3 内の位置はマニフェストの `"after"` で指定する
   （detranspile フックが対応）。`<名前` や `:名前` は無い武器もあり、欠けは許容される。
   * カードの中身は下記「ショップカード」参照（武器の絵ではなくテキストカード）。
5. **テスト**: Weapon_name.itemNum（新武器）= 期待位置、弾プログラムの値、
   反動比、連鎖フックの発火/取消を検証する。

## バナー（キャラ詳細カード）

- ツリー画面でノードを選ぶと `Character_name + " banner"` のコスチュームが
  スタンプされる（Pen_All のツリー描画、Stamp 呼び出し）。名前が 1 文字でも
  ずれると詳細カードが無言で出ない。新キャラには必ず作る。
- 構造: 既存キャラの banner をコピーして作る。キャンバス 471×115、
  回転中心 (235.5, 57.5)。テキストは tspan が 6 個並ぶ:
  **[英語名, 日本語の二つ名, フレーバー文 ×4 行]**。位置で対応するので
  順番を崩さず中身だけ差し替える（例: Gobo = "Gobo" / 「火山の鉄人」/
  「Goboはかつて火山地帯に」「住んでいた。」「毎日、集落に降り注ぐ落石に」
  「耐えるため防御力が優れている。」）。
- 帯の色はそのキャラのテーマ色（SVG 内の図形側）。流用元の色のままでも
  動くが、キャラの色に寄せるのが既存の並び。
- 二つ名とフレーバー文はユーザー向けコピー。起案はしてよいが仮置きとして
  報告で明示する。

## ショップカード（武器の * コスチューム）

- * カードに武器の絵はない。**テキストだけ**のカード: 上部にカテゴリ表記
  （例: "Strike"）、英語名、説明文（複数行）が SVG 内のテキストで描かれる。
  既存カード（同カテゴリのもの）をコピーし、テキストと配色だけ差し替える。
- 説明文はユーザー向けコピー。性能（ダメージ・連射・反動など）がデータと
  一致しているか必ず照合する。起案は仮置きとして報告で明示する。
- **【最重要】ショップの品揃えは「*」コスチュームの連続ブロックで決まる**:
  Set_val が *Gun から nextCostume で辿り、最初に「*」でない名前に当たると
  停止する。新アイテムの * カードは必ずブロック内（既存の同系統カードの直後）
  に置くこと。TS 側の登録アンカーと manifest の "after" の両方をブロック内に
  指定する（after 無しだと sb3 では末尾へ落ちてブロック外＝店に並ばない）。
  原作の *マジックワープ はブロック外で、マジックワープは店に並ばない（原作仕様）。
- @ アイコンは流用元武器の @ と同一キャンバス・回転中心で描く
  （抜刀剣は @大剣 の 36×34 に合わせた）。

## コスチューム / SVG の規則

- 登録は **2 箇所必須**: `src/distilled/Pen_All/assets.ts` のコスチューム表と
  `tools/mythology-costumes.json`（detranspile フックが sb3 へ注入）。
  片方だけだと TS では出るが sb3 に入らない（逆も同じ）。
- **顔の向き**: コスチュームは **+x（右）向き**で描かれ、頭頂は **−x 側**。
  正面ポートレートは画像を 90° CW 回転した姿。装飾を置く前に原画を回転させて
  解剖（目・頭頂・顎の位置）を確定する。ユーザーが「顔がどこか理解してない」と
  指摘した実績のある最重要ポイント。
- **色**: 原作パレットから実測した色だけを使う（赤 #ff0000、金 #e8aa00、
  オレンジ #ff6e00、水色 #00f2ff、緑 #2aff00、ピンク #ff00dc、紫 #7664ff、
  紺 #00064d、灰 #9a9a9a、濃灰 #333333、黒、白）。
  ユーザーの作風指示には即従う: 色を変えるなと言われたら塗り自体の加工
  （グラデーション化など）に切り替え、上に物を描き足さない。
- コスチュームはタイトにトリミングされている（余白なし）。装飾は体の輪郭の
  内側か上に重ねる。輪郭の外へはみ出す楕円などは汚れに見える。
- 新規 SVG は既存武器・キャラと同一キャンバス/回転中心で作ると
  ゲーム内の位置合わせが不要になる（抜刀剣は大剣と同一にした）。
- プレビューは body+ / body++ / ポートレートの 3 面で目視確認してから出す。

## サブ武器の経済（Item_list のフィールド意味）

- 実効ストック = 容量（field2）× 倍率（field4）。使用で field2 ずつ減り、
  回復は FPS_temp/フレーム固定。つまり **field2 が「1 回分のチャージ時間」**
  そのもの（小さいほど速く貯まる）。「N スタック」= field4、「貯まる速さ」= field2。
- 武器の発射音は Item_list の弾名（idx12）と同名のサウンド。同名サウンドが
  無いと無音になる（新規合成音は manifest に "sound": true で登録）。

## ガード系サブ（1マスガード等）

- 設置は Shot_create の「1マスガード」分岐が C<武器名> レコードを作る。
  Bullet_list に C<武器名> プログラムが要る:
  ["C<名>", "Guard", 耐久, "6", 摩耗率, 破壊時の生成物, "7", "-", 1.5, 0]
  耐久 = 被弾蓄積の上限（一番弱い弾でも蓄積 ≈ 1.7 × 攻撃補正なので、
  「一回で壊れる」は耐久 1）。摩耗率は未被弾時の寿命を決める（耐久 ÷ 摩耗 ÷ FPS_temp フレーム）。

## 既存武器の弱体/派生版（op の写し）

- 特殊武器の op（例 "About shield cannon"）はダメージ等が**ハードコード**で
  引数を取らない。派生版は Bullet_action 内に新 op 分岐を写して数値だけ変える
  （実績: "About shield cannon light" = Damage 50→17、爆発 10/8/5→3/3/2、炎は青）。
- 派生アイテムの behavior 文字列は本家と同じにすると Shot_create のマズル・
  煙などの特殊処理を流用できる。レコード名 = アイテム名になるため、引く
  プログラムは派生側のものになる（Bullet_list に派生名のプログラムを置く）。
- 時間制限つきの自己強化（装甲など）はクラスフィールドのタイマーで持つ:
  Shot_create の先頭で「武器名一致 かつ 発射者が自分（P.item(1) == G.ID）」の
  ときにタイマーをセットし、効果は All の速度計算（本家のシールド回復の直後）
  へフックして毎フレーム減算する。他人の発射で自分のタイマーが立たないよう
  ID チェックを必須にする（テストでも検証する）。

## バフ追加の規則

- Buff 表（20 フィールド/件）と Buff_name は**位置で対応**する。Buff_name は
  72 件、表は 79 件あるが、新規バフは表の 72 番へ**挿入**し Buff_name へも
  同じ位置に足す（末尾追加は対応がずれて静かに壊れる）。
- バフアイコン "^<バフ名>" コスチュームが必須（無いと表示で化ける）。
- 秒数は 30fps 換算のフレーム数で書く（10 秒 = 300）。Put_buff の第 2 引数が持続フレーム。

## 落とし穴一覧

- ステージリストの初期値は原作 project.json が正。TS 側リストの編集だけでは
  sb3 に入らない。buildSb3 の「ステージリスト上書きフック」
  （対象: Character / Character tree / Item list / English weapon name /
  Bullet list / Buff）が TS から sb3 へ同期する。新しく別のステージリストを
  編集対象にしたらフックの対象表へ足す。
- **detranspile は新規手順（メソッド）を作れない**。TS に新しいメソッドを足して
  他から `yield*` で呼ぶとビルドが `yield* unknown method` で落ちる。新規の
  毎フレーム処理は、既存手順の末尾へゲート付きで直接書く（実績: スロット本体を
  Draw_NPC 末尾に num==7 かつ Menu[19]==7 の条件で配置。状態は Pen の
  クラスフィールドに持つ）。呼ばれない新規メソッドを残すと TS テストだけ通り
  sb3 に入らないので絶対にやらない。
- ロビー NPC の追加: All のロビー節に Draw_NPC 呼び出しを追加し、Draw_NPC 内に
  num 別の初期化分岐を足し、All の「離れたら Menu[19]=0」リセット条件にも
  新 num を足す。Draw UI の内容ブロックは Menu[19] の値ごとにゲートされている
  ため、新モードでは既存 UI は何も描かない（独自 UI を描く余地がある）。
  通貨は G.Money（ショップと共通）。
- 円形ガード: Shot_create に新 behavior を足し、フラットな const 配列
  （[dx, dy, 角度] × N、SUPER_EFFECTS 方式）で各マスへ C レコード＋
  Create_guard を呼ぶ。Temp1 = 外向き角度にすると Guard の向きは +180 で
  格納され、外からの弾だけ受ける（内側からは撃ち抜ける）。
- 止めないフィールド（スライム等）: Guard リストへ登録しなければ弾は止まらない。
  効果は Step 手順のフックで「弾の今いるマスに該当レコードがあるか」を
  走査して速度を変える。寿命だけなら [Length, 8, 上限, "-"×6] のみの
  プログラムでよい。設置物の見た目は ":名前" コスチューム（Draw_bullet が
  全レコードを ":" + 名前でスタンプする）。
- detranspile は `B()` を含む入れ子三項演算子で壊れる。if 代入に書き直す。
- detranspile（TS→ブロック変換）は素のブロック文 `{ ... }`、`break`、
  ブロック本体なしの for 文を受け付けない。フックはメソッド直下の文として
  書き、ループ脱出はカウンタへ終端値を入れて行う。
- 弾レコードのプログラムから所有者本人を動かすことはできない（Set position は
  逆向き）。ワープ等は Weapon_motion 先頭の MYTHOLOGY フックで
  「自分のレコードが壁セル（round(x/50)/round(y/50) ∈ Bullet_wall）」を
  検知して処理する。直前位置はプログラム側で CS val の "[3" / "[4" 参照を
  使ってレコードの空きフィールドへ毎フレーム控える。
- const 配列への動的添字アクセスは Scratch リストとして実体化する
  （0 始まり +1 のずれに注意）。
- テストでクリック発火を駆動するには `pen.Clicking='1'` と `pen.Mouse_touch` の
  事前設定が要る。
- クラウド形式は固定長。`Special_skin` は field 25 の 1 文字なので
  段階追加は "2" までなら形式不変で入る。
- 効果の語彙は既存の `Bullet_name` / `Buff_name` にある名前だけ。
  完全新規の効果は Player_shot 側の処理追加が別途必要。
- /tmp は VM 入替で消える。成果物とプレビューは `~/workspace/` に置く。

## State E で学んだこと（2026-11-23 追記）

- **Shot_create の分岐は create_type のキーワード**（普通 / 設置 / 中央 / 魔法 / ガード等）。

## State F で学んだこと（2026-11-23 追記）

- **弾には必ず「:弾名」コスチュームが要る**: Draw_bullet は `":" + レコード名` の
  コスチュームを切替えて描く。無いと切替が失敗して何も描かれず、弾が完全に見えない
  （エラーも出ない）。新しい弾プログラムを作ったら `:` 付き弾スプライトを
  make_new_costumes.py に登録すること（アンカーは既存の「:」系コスチューム）。
- **特殊武器モード（搭乗）の入り方**: 現在の Inventory_2（31 フィールド）を
  Temp_inventory へ退避 → G.Special_weapon = "1" → Inventory_2 を
  5 枠×6 フィールド＋末尾 "1" で再構築 → Set_inventory__T1__T2__T3(offset, 名前)
  で各枠を埋める。**枠数は枠1のタイプ字段（item 2）を Special_weapon_2 で引いて
  決まる**ので、枠1のタイプは必ず Special_weapon_2 に載っている名前にすること
  （サブタイプでは解決できない）。発射可否（Full）は Item_list ではなく
  **枠の字段 3（残弾）/ 4（容量）が正**。終了時は Temp_inventory から 31 フィールド
  復元＋Special_weapon = "0"（Respawn の復元と競合しないよう、モード専用フラグと
  Special_weapon == "1" の両方を条件にする）。
- **ワープ系の発生位置**: 銃口位置（muzzle 50 先）は壁セル内になり得る。壁に
  張り付いて撃つ前提で、生成直後に発生セルが Bullet_wall に含まれる間は
  発射者側へ引き戻す調整を入れる（ワープ先が壁の中になるグリッチの防止）。
- **ドローン等の操縦体**: 壁判定は `round(x/50) + "/" + round(y/50)` を
  G.Bullet_wall.contains で見るのが既存パターン。軸分離で判定すると壁ずり移動ができる。
  本体からの距離制限は毎フレーム円周クランプで足りる。

## State G で学んだこと（2026-11-23 追記）

- **武器名と弾プログラム名は完全一致が必須**: Shot_create は武器名でレコードを
  作り、Bullet_action はレコード名でプログラムを引く。名前がずれると弾が
  無言で機能しない（Chase gun のプログラムを "チェイスガン" とした事故）。
  英語名の武器はプログラム名・Bullet_name・":弾名" コスチュームも英語名で統一する
- **detranspile は Math.min を受け付けない**（"call .min on Math" でビルドが落ちる）。
  compare + if 代入で書く。Math.round / Math.max / Math.floor は既存フックで使用実績あり
- **Bullet_list.itemNum は最初の一致を返す**: 生成物名として他プログラムに
  現れる名前（例: ブラックホール）は itemNum で引けない。テストでは末尾からの
  位置計算で取る
- **起爆信号パターン（隠しアイテム方式）**: 「構えている間だけボタンになる」武器は、
  Weapon_motion フックで (1) Menu[75] を張り付けて通常のサブ連射を止め、
  (2) スロット名を隠しアイテム名へ一時差し替えして Shot__c(Inventory, true) を
  強制発射（残弾は保存・復元して消費させない）、(3) Shot_create 先頭で隠しアイテム名を
  検知して本来の処理（レコードのフラグ立て等）を行う。信号はクラウド経由で
  全クライアントに届く。隠しアイテムにも Item_list レコードと English エントリが
  要る（件数一致）。カードやコスチュームは付けなければ店に並ばない
- **マップタレット（Cannon）の砲弾**: 着弾効果は砲弾プログラムの Length/Delete の
  生成物で決まる。生成物を差し替えれば着弾効果ごと変えられる。プレイヤーを
  引き寄せる等の「プレイヤーを動かす効果」はプログラムでは不可能なので、
  All 内のフックで自分の位置を動かす（スライムの Step フックと同じ考え方）。
  中心ダメージはプログラムの Damage(値, 距離, 1, "ND", ...) が全体攻撃として
  毎フレーム蓄積するので両方を組み合わせられる

## State H で学んだこと（2026-11-23 追記）

- **復号は Item_list idx10（コスチューム名）を武器名として Player_shot へ渡す**:
  Shot_create で武器名に依存する処理（起爆信号のような隠しアイテム、モード突入
  フック等）を持つアイテムは、idx10 を必ずアイテム名自身にすること。
  idx10 が別の名前だと信号がその武器の通常発射に化ける。しかも復号経路の
  Shot_create は残弾を消費しないため、「信号が設置に化ける」と無限設置になる
  （C4起爆の idx10 = "C4" 事故）。テストは復号が渡す名前
  （Item_list.item(flat+10) / +11）で Shot_create を駆動して回帰を防ぐ
- **弾プログラムの命令アリティを厳守する（特に Length = 8 引数）**:
  Length は [フィールド, 上限, 生成物×6] を消費する。[Length, 7, 60, "Damage", ...]
  と書くと Damage 命令が生成物に食われて実行されず、寿命切れで "Damage" という
  レコードに化ける。そのレコードはプログラム検索に失敗して Bullet_list 先頭
  （ピストル）のプログラムで動き続け、ダメージ 25 の見えない幽霊弾になる
  （ドローン弾 / Chase gun / ブラックホールで発生）。寿命で素消えさせたい場合は
  生成物に "-"×6 を明示する。ピストルのプログラムが正形の見本。
  新規プログラムはアリティ表でパース検証してから入れる
- 命令アリティ早見（実測）: Step 1 / Search first 2 / Homing 2 / Mouse homing 2 /
  CS val 3 / IF 3 / Stamp 3 / Mine stamp 3 / Screen stamp 3 / Sword damage 4 /
  Delete 6 / Break wall 6 / Create 7 / Length 8 / Damage 9 / Guard 8

## State I で学んだこと（2026-11-23 追記）

- **Scratch の保存上限は project.json 5MB**: 原作も超過する TurboWarp 前提
  プロジェクトなので、Scratch で保存・公開したい場合は圧縮が必須。
  buildSb3 末尾に圧縮パスが入っている（ブロック ID と変数/リスト/放送 ID の
  短縮付け替え＋ shadow/topLevel の false 省略）。project.json は
  5.6MB → 4.0MB まで落ちる。ID は VM が保持するのでエディタ再保存でも
  小さいまま。圧縮後も verify-distilled のダイジェストが完全一致すること
- コンテンツ追加で project.json が再び 5MB に近づいたら、まず ID 圧縮が
  効いているか（minify ログ）を確認する。それでも超える場合はブロック数
  そのものを削る必要がある
- クラウド変数は「☁ CLOUD1〜10」の 10 個（Scratch の上限ちょうど）。
  新しいクラウド変数は追加できない
