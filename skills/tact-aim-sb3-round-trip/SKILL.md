# TACT-AIM sb3 往復検証

対象: `TACT-AIM-MYTHOLOGY` / `TACT-AIM-MOD`（TS → sb3 の detranspile を使う全 MOD）。
コンテンツ追加のたびに回す検証ゲートのうち、sb3 側の部分。

## 再生成と構造検証（毎回必須）

```sh
mkdir -p out && npm run detranspile:build-distilled
python3 tools/validate_sb3.py out/*.sb3   # 0 issues が必須
bash tools/verify-distilled.sh            # BOOT TEST: PASS = 往復等価
```

- 構造検証を毎回回し、**異常0件**を確認して初めて成功と報告する。
- sb3 の中身を直接確認する: 新コスチュームの存在、マニフェスト全アセットの同梱、
  ステージリストの長さ、クラウド変数が CLOUD1〜10 のみ。
- 成果物を所定の場所へコピーし、`out/` は消す。

## なぜ構造検証が別に要るか

- 引数レポーターは出現順ではなく**引数名で**対応付けて確認する。
  文の削除・挿入で出現順のキューがずれると、レポーターが文の位置に落ちる。
- モニター表示ブロックは引数レポーターと分けて確認する。モニター側の破損は
  実行時 no-op で、起動テストも挙動も変わらない。
- **ダイジェスト一致と起動テスト合格だけでは不十分。**
  2026-11-22 の TurboWarp IR エラー（"argument_reporter_boolean"）は両方を
  通過し、実機で初めて発覚した。構造検証はその再発防止として入った。

## 起動ダイジェストの再基準化

データ追加でダイジェストが変わるのは正常。ただし無条件に新しい値を正としない:

1. 状態ダンプ（boot 15,000フレーム後の G 全項目: スカラー全量＋リストは
   長さ・全要素ハッシュ・先頭3件＋penLines/stamps/errors/threads）を新旧で取る。
   旧側は `git worktree add /tmp/oldbuild HEAD` + `npm ci` + `npx tsc`。
2. diff が「追加データ由来のリスト長と中身」だけであることを確認する。
   スカラーや描画カウンタに差が出たら実装ミスを疑う
   （NPC のスタンプ増加など、説明できる描画差は内訳を計算して一致を確認する）。
3. `tests/boot.test.mjs` の EXPECTED_DIGESTS を更新し、ファイル内の履歴コメントの
   書式に倣って「日付＋何を追加したか＋全比較で差分が何だけだったか」を追記する。

## TurboWarp IR エラーが出たら

- スタックブロックを名指しする IR エラーは、ユーザーの端末の問題ではなく
  **emitter（detranspile）の構造的な故障**として扱い、ゲームコードより先に
  emitter のキューを疑う。
- 名指しされたスクリプト周辺の生成ブロックを見て、文の位置にレポーターが
  落ちていないか、直近の削除・挿入で対応がずれていないかを確認する。
- 修正後は全テストと往復を回し直し、sb3 を再生成して構造検証を再実行してから渡す。

## 修正の適用先

- emitter の修正は、故障が見つかったコピーにまず入れ、そこで確認してから他へ広げる。
- MOD 側で見つかった修正を蒸留版（原作の純粋コピー）の main へ入れるかは、
  作者の判断を仰ぐ（蒸留側の変更は原則しない。一般則として
  「ランタイムの再現漏れは本体側が正筋」と作者が許可した範囲は例外）。
- 報告には sb3 の再生成・構造検証の件数・テスト件数をセットで書く。
